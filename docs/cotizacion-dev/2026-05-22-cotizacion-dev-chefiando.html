Contexto del proyecto

Qué es Migraflix / Chefiando

Plataforma que ayuda a restaurantes con:

  • Gestión de contenido (fotos, copy) generado por IA.
  • Publicación en Instagram.
  • Próximamente: bots de atención al cliente, SEO automatizado, presencia en directorios.

Hoy es admin-only: el equipo de Chefiando edita en una interfaz web (/admin/*) la data que se publica luego en IG (vía n8n + flujos manuales).

Volumen actual: ~500 brands en Airtable, ~10k contenidos.

FEATURE 01 · PRIORIDAD P0

Login IG + Multi-tenant + Publicación (Feed / Stories / Reels + Agendar)

Estimado dev
_______
Depende de
— Fundación
Stack
Meta Graph API · OAuth

Contexto

Hoy Migraflix es admin-only. Los restaurantes (Brands en Airtable) no tienen cuenta propia y la publicación a Instagram es manual o vía n8n.

Necesitamos que cada restaurante entre con su propia cuenta de Instagram, vea solo su Brand, y pueda publicar contenido (feed, Stories, Reels) ahora o agendado con un clic.

Diseño técnico

Flow OAuth

[Restaurante en /dashboard/login]
   → click "Entrar con Instagram"
[/api/auth/instagram] → redirect a Meta OAuth
   → usuario autoriza
[/api/auth/instagram/callback]
   → exchange code → short-lived → long-lived (60d)
   → GET /me?fields=username,account_type
   → detectar Business vs Personal
   → findBrandByInstagramId() o findBrandByHandle()
   ├ match → guardar token, set cookie, redirect /dashboard
   └ no match → redirect /dashboard/vincular

Schema Airtable — campos nuevos en Brands

CampoTipoNotas
instagram_user_idTextID numérico de IG
instagram_usernameTextHandle sin @
ig_access_token_encryptedLong textAES-256-GCM
ig_token_expires_atDateTime60 días desde emisión
can_publishCheckboxTrue solo si Business
last_login_atDateTimeÚltima entrada del brand

Schema Airtable — nueva tabla ScheduledPosts

CampoTipoNotas

media_urlURLFoto o video (GCS)
cover_urlURLSolo Reels

scheduled_forDateTimeCuándo publicar

Endpoints de publicación

TipoFlow IG Graph API
FeedPOST /{ig_user_id}/media (image_url) → /media_publish
StoryPOST /{ig_user_id}/media (image_url, media_type=STORIES) → publish
ReelPOST /{ig_user_id}/media (video_url, REELS, cover_url) → poll status → publish

Riesgos F1

  • Meta App Review tarda 2–6 semanas (bloqueador externo, no contado en horas dev). Empezar trámite el día 1.

  • Handle de Airtable no siempre coincide con username real de IG. Normalización robusta.
  • Reels processing async: IG tarda 30s-5min en procesar video. Cron debe poll status.

FEATURE 02 · PRIORIDAD P1

Bots IA por Restaurante — WhatsApp + Voz

Estimado dev
_______
Depende de
F1
Stack
SendPulse · nlpearl · Claude

Contexto

Hoy Chefiando atiende consultas de clientes finales (comensales) manualmente desde el WhatsApp del restaurante. No hay automatización de voz. Pierde consultas fuera de horario y no mide CSAT.

Objetivo: bot 24/7 que responde menú, horarios, ubicación, reservas básicas (WhatsApp) y opcionalmente atiende llamadas con bot de voz que toma pedido/reserva y escala a humano.

Stack decidido

W
WhatsApp · SendPulse
Ya pago + integrado. Evaluar wacrm como benchmark en POC inicial.
V
Voz · nlpearl
Elegido por cliente. Orquesta STT + LLM + TTS.
L
LLM · Claude Haiku 4.5
Default GNB. Bajo costo/latencia para conversación.
K
Knowledge base · Airtable
Per-brand. Sin vector store en MVP. Prompt context suficiente.

Schema Airtable

BotConfigs (1 row por brand): brandId, whatsapp_enabled, voice_enabled, whatsapp_number, voice_number, bot_persona, menu_json, horarios, direccion, faqs_json, handoff_keywords, handoff_notify_phone.

Conversations (1 row por conversación — patrón anti-bloat): brandId, channel, customer_id, messages_json, messages_count, tokens_used, cost_estimated_usd, duration_seconds, created_at, last_message_at, closed_at, status, csat_rating.

Conversations_Archive — mismo schema, recibe rows >90 días vía job mensual.

FEATURE 03 · PRIORIDAD P2 · QUICK WIN

Auditoría Sentry + Triage + Integración Linear

Estimado dev
_______
Depende de
—
Tipo
Observabilidad

Contexto

Sentry ya está instalado (sentry.client.config.ts:1-78) pero:

  • No hay certeza que el DSN esté seteado en Vercel producción.
  • 9+ docs en /docs/ sobre Sentry — señal de que la config fue dolorosa y no quedó cerrada.
  • No hay alertas, no hay runbook, no hay integración con Linear.

Objetivo: dejar Sentry en estado "Listo" — auditoría + triage + alertas + loop Sentry↔Linear.

Diseño técnico

4 fases

  1. Auditoría: validar DSN en Vercel, source maps, sampling, ignoreErrors.
  2. Triage: API Sentry → lista de errores activos → reporte priorizado.
  3. Alertas: 3 mínimo (nuevo error / spike / crítico) hacia Slack o email.
  4. Integración Linear: webhook Sentry → crear issue. Linear Done → resolve Sentry.
[Sentry detecta issue] → webhook → /api/integrations/sentry-to-linear
   → Linear API: create issue
   → Mapping guardado en Airtable

[Linear issue Done] → webhook → /api/integrations/linear-to-sentry
   → Sentry API: resolve

Riesgos F3

  • Webhook loop si Linear resuelve y Sentry re-abre por nuevo evento. Mitigación: ignorar reaperturas <30 días.
  • Spam de issues Linear. Mitigación: crear issue solo si level >= warning Y users_affected >= 2.

FEATURE 04 · PRIORIDAD P1 · MAYOR ALCANCE

SEO Automatizado — Landings Multi-Dominio + GMB + Directorios

Estimado dev
_______
Depende de
F1
Sub-sistemas
A · B · C · D

Contexto

Los restaurantes hoy: sin landing pública optimizada (invisibles en búsqueda local), GMB semi-abandonado (horarios desactualizados, sin posts, sin respuesta a reseñas), ausentes en directorios LATAM relevantes.

Objetivo: automatizar presencia SEO/SEM local con 3 sub-sistemas + trackeo unificado.

A · Landings públicas multi-dominio

3 modos de URL, resolución por host:

[Request entra con host X]
   → middleware
   → si X = migraflix.com → URL /r/[slug]
   → si X = *.migraflix.com → match Brand.subdomain → rewrite a /r/[slug]
   → si X es dominio custom → lookup BrandDomains → rewrite a /r/[slug]

Campos nuevos en Brands: slug, subdomain, subdomain_enabled.

Nueva tabla BrandDomains: brandId, custom_domain, status, verification_token, ssl_status, connected_at, vercel_project_alias.

B · Google My Business

  • OAuth Google (scope business.manage) → tokens encriptados.
  • Sync diferencial diario: horarios/fotos/menú Airtable → GMB.
  • Posts con IA (3 variantes) + rate limit (max 1/día, 3/semana).
  • Reseñas: NUNCA auto-publish. IA propone, humano aprueba.
  • Métricas diarias: vistas, llamadas, direcciones.

C · Directorios externos

Shortlist 10 LATAM: TripAdvisor, OpenTable, PedidosYa, Rappi, Restorando, Cuponatic, Listado, Yelp, Foursquare, Zomato. Realista: 4-5 con API + 2-3 con autofill semi-asistido. No scraping.

D · Trackeo de conversiones

Tabla SeoEvents (1 row por brand-día, agregado): event_type (call/directions/reservation/landing_view), source (landing/gmb/directory). Reporte unificado por canal + dominio.

Riesgos F4

  • Penalización GMB por spam — rate limit + variación IA + max 1 post/día.
  • Directorios sin API — solo APIs oficiales + autofill semi-asistido. Nunca scraping.

  • Vercel Pro requerido — wildcard + custom domains no soportados en Hobby.
  • SSL provisioning — Vercel a veces tarda. Cron re-intenta y alerta si >24h.

Riesgos globales y dependencias

Grafo de dependencias

F3 (Sentry) ─── independiente, arrancar primera semana
                ↓
F1 (Login IG + Multi-tenant) ─── FUNDACIÓN, todo lo demás depende
   ├──→ F4 (SEO + GMB + Landings)    usa sesión de restaurante

Riesgos globales

1. Meta App Review (F1) — 2-6 semanas de bloqueador externo. Empezar trámite el día 1.
2. Costos variables sin cobro (F2 + F4) — Chefiando absorbe LLM + voz + WhatsApp + GMB. Definir umbral mensual y revisar mensualmente.
3. Airtable como DB de tablas que crecen — Conversations (F2) y SeoEvents (F4). Trigger de migración: >30k rows/mes O >1.500 brands → cotizar Supabase aparte.
4. Vercel Pro necesario — F4 requiere wildcard domains + custom domains. Hobby no soporta. Confirmar plan antes de empezar.
5. Calidad de prompts/IA (F2, F4) — dependen de datos del brand. UI guiada + piloto antes de rollout masivo.
